# Companion Auto Summon development instructions

- The approved external title is Companion Auto Summon for No Man's Sky, with the byline "by Lineum Dynamics". Keep the in-game short title Companion Auto Summon and repository slug `nms-companion-auto-summon`. Code/class identifiers, filenames and legacy `NMS-AutoPet` data and development-runtime paths remain stable; do not silently reset or migrate player data for branding.
- Use the complete Nexus page title `Companion Auto Summon for No Man's Sky - by Lineum Dynamics` in the site's Mod Name field; its validation requires the ASCII hyphen. Promotional covers must visibly include the title, game qualifier and author credit, even when split across lines. Nexus renders its own heading over the header image: keep that background dark and subdued, without embedded text or white elements, to preserve text contrast.
- Use one modest author credit in the main presentation or an appropriate About surface; keep native setting captions focused on their function. Do not claim an in-game credit is implemented until it exists and is verified. A future player-facing credit requires the same catalog updates as other UI text.
- The canonical source is https://github.com/lineum-dynamics/nms-companion-auto-summon. Public GitHub source and an explicitly labelled prerelease are authorized after the first Nexus alpha. Verify remote visibility before claiming completion. Installed game-test copies and old exported packages are outputs, not parallel development roots.
- All future commits in this repository must use `core@lineum.io`. The owner approved retaining existing author metadata in public history; do not rewrite history for that reason.
- Read `DEVELOPMENT.md`, `DESIGN.md`, `LOCALIZATION.md` and the current manifest before changing behavior or compatibility claims.
- All source code, identifiers, comments, docstrings, test names, tooling, developer diagnostics, canonical documentation and document filenames must be English. This includes internal evidence, installation requirements and release planning. Translated player-facing values belong in separate locale resources. Preserve Unicode coverage in test data.
- Review localization impact in every change. Every player-facing UI text or meaning change must update the canonical English entry and all affected language entries in the same change, without exception. Code-only changes do not require pointless translation rewrites. The nine compatibility-launcher messages are cataloged; other launcher text and the development panel still need coverage before changing their wording. Do not silently leave changed text outside this rule.
- Keep translated entries' source fingerprints synchronized with the actual reviewed English meaning. Never refresh fingerprints merely to hide stale translations, copy English as an undeclared placeholder, or claim unreviewed drafts are verified translations. Run `python -B tools/validate_locales.py` and its focused tests before build/package; validation failure must stop output creation. Native-menu/HUD catalogs do not establish runtime language selection, glyph support or coverage of the whole application.
- Update the affected documentation and changelog in the same change as code. Clearly distinguish implemented behavior, offline checks, live observations and planned features.
- Keep native ownership, eligibility and placement rules intact. Do not generate or unlock pets, lower existing gameplay limits or write game save files. The approved earned exosuit-technology design may add its own recipes and energy cost; prototype it offline until native registration, transactions, persistence and removal are verified. Never grant prototype inventory to the player's normal save.
- Keep the exact executable guard and use verified native mappings. A new game build is not supported until its mapping and behavior have been checked. Unknown or unreadable versions must disable native integration before hooks or native calls. The final launcher must explain this outside the game, with maintained translations and no unsafe override; a disabled runtime alone does not establish safety for saved custom technologies.
- Run compatibility-profile validation before builds and packaging. Preserve the actual-process-handle check before each DLL injection, the independent native class guard, exact launch configuration and refusal of foreign pyMHF libraries. A matching selected installation is not sufficient evidence for another process selected later by the framework.
- Do not modify an installed runtime while NMS is running. Do not kill NMS or close/terminate its pyMHF host. Before a new live trial, preserve current progress and verify a fresh backup as needed.
- Source tests and packaging must not launch, attach to or modify the game. Packaging must not deploy implicitly.
- Keep personal saves, accounts, credentials, settings, logs, raw game disassembly and copyrighted game binaries out of Git and release ZIPs.
- The public target is an easy portable installation, native-looking feedback, safe X-menu settings and verified language coverage. The current candidate does not yet implement all of these; do not claim otherwise.
- Inspect Git status before editing and preserve unrelated changes. Remote creation, pushes and public publishing are separate from local version control; use the user's actual authorization and never guess the destination account.
- Keep experimental features on named feature branches. The native alpha installs by merging the packaged Binaries/GAMEDATA folders and starting through Steam; no separate launcher is required.
- The owner requests regular uploads of validated, versioned test archives. Nexus mod 4579 was published as the first EARLY ALPHA on 28 September 2026; native file 49202 is Main / Primary and older files are archived. Package only an explicit release-file allowlist, excluding personal settings, saves, logs, caches and research assets. Describe offline versus live verification and preserve the prior working test version. Alpha publication does not authorize labelling unverified behavior stable.

Explicitly labelled translations such as `README.cs.md` and locale resources may contain their target language. They are translations of the English canonical material, not an exception for internal or developer documentation.

- For the 0.9.2-test player distribution, document the root Companion Auto Summon.exe and bundled Python runtime. Do not direct portable testers through Python/pip/PowerShell setup. Keep those instructions explicitly scoped to retained developer packages. Windows .NET Framework 4 and Microsoft Visual C++ v14 x64 prerequisites remain explicit.
- Normal portable starts require a private verified backup before launch. Preserve external preferences and stage a verified working mod copy into private sessions rather than writing runtime caches/logs into the extracted distribution. Never include personal backups, logs or sessions in a public ZIP.
- The owner may pass the unchanged validated ZIP to the second Windows/Steam tester. Record exact ZIP identity and upload/readback in docs/release/TESTER-HANDOFF.md; do not claim a pending upload, delivery, installation or multiplayer test as completed. The former unpublished-draft restriction was superseded by explicit public-alpha authorization.

- The 0.10.0-native-test candidate uses C++ with pinned Ultimate ASI Loader and MinHook, with no Python player dependency or external settings panel. Installation merges the explicit Binaries/GAMEDATA overlay, then starts normally through Steam. Never overwrite a different existing winmm.dll or run native and legacy Python versions together. Preserve the old portable instructions as version-scoped history.
- Native activation requires a verified private snapshot before gameplay hooks, while the game process is already running. Label it pre-activation, never closed-game/pre-launch. Preserve the separate verified closed-game backup before the first native trial. Never modify original saves, automatically restore a backup or weaken verification after a failure.
- Keep packaged candidate bytes and their build/validation/package receipts immutable. Record subsequent deployment, player observations and Nexus outcomes separately. Queue acceptance and logical activation are not proof of visible companion appearance.
