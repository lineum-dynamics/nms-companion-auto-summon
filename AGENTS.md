# Companion Auto Summon development instructions

- The approved external title is Companion Auto Summon for No Man's Sky, with the byline "by Lineum Dynamics". Keep the in-game short title Companion Auto Summon and repository slug `nms-companion-auto-summon`. Code/class identifiers, filenames and legacy `NMS-AutoPet` data and development-runtime paths remain stable; do not silently reset or migrate player data for branding.
- Use the complete Nexus page title `Companion Auto Summon for No Man's Sky - by Lineum Dynamics` in the site's Mod Name field; its validation requires the ASCII hyphen. Promotional covers must visibly include the title, game qualifier and author credit, even when split across lines. Nexus renders its own heading over the header image: keep that background dark and subdued, without embedded text or white elements, to preserve text contrast.
- Use one modest author credit in the main presentation or an appropriate About surface; keep native setting captions focused on their function. Do not claim an in-game credit is implemented until it exists and is verified. A future player-facing credit requires the same catalog updates as other UI text.
- The canonical source is https://github.com/lineum-dynamics/nms-companion-auto-summon. Public GitHub source and an explicitly labelled prerelease are authorized after the first Nexus alpha. Verify remote visibility before claiming completion. Installed game-test copies and old exported packages are outputs, not parallel development roots.
- All future commits in this repository must use `core@lineum.io`. The owner approved retaining existing author metadata in public history; do not rewrite history for that reason.
- Read `DEVELOPMENT.md`, `DESIGN.md`, `LOCALIZATION.md` and the current manifest before changing behavior or compatibility claims.
- All source code, identifiers, comments, docstrings, test names, tooling, developer diagnostics, canonical documentation and document filenames must be English. This includes internal evidence, installation requirements and release planning. Translated player-facing values belong in separate locale resources. Preserve Unicode coverage in test data.
- Review localization impact in every change. Every player-facing UI text or meaning change must update the canonical English entry and all affected language entries in the same change, without exception. Code-only changes do not require pointless translation rewrites. The nine compatibility-launcher messages are cataloged; other launcher text and the development panel still need coverage before changing their wording. Do not silently leave changed text outside this rule.
- Keep translated entries' source fingerprints synchronized with the actual reviewed English meaning. Never refresh fingerprints merely to hide stale translations, copy English as an undeclared placeholder, or claim unreviewed drafts are verified translations. Run `python -B tools/validate_locales.py` and its focused tests before build/package; validation failure must stop output creation. Native-menu/HUD catalogs do not establish runtime language selection, glyph support or coverage of the whole application.
- Update the affected documentation and changelog in the same change as code. Clearly distinguish implemented behavior, offline checks, live observations and planned features.
- Maintain `docs/KNOWN-ISSUES.md` as the canonical record for the exact current public mod/game build. Mirror a concise, user-facing Known Issues section in the GitHub README and Nexus description, with a link to the canonical record. Update all three when a credible report changes status or a release fixes/issues new behavior. Record observed symptoms separately from suspected causes, note workarounds and fix verification, and do not remove an issue until its fix is included in a validated public build. Never publish private logs, save data, account identifiers or machine paths.
- Review `docs/release/NATIVE-RELEASE-GATES.md` before changing an alpha/prerelease label. Report functional acceptance, upload/listing, actual download availability and scanner review separately. Recheck dated scan reports for both the exact new artifact and the previous public artifact; an earlier Nexus acceptance or low detection count is not current clearance. If OS protection blocks an input, record a blocked-input/tool error and continue only with other authorized evidence; never restore it, add exclusions or access another copy to bypass protection. Preserve the exact submitted bytes while investigating a concrete source/build defect.
- During publication, inspect every retained Main file as well as the replaced file. Keep superseded releases under Old with explicit game targets, preserve bytes/history, and read back categories. Old files can retain download links; neither a category nor a visible link establishes scanner clearance or downloaded-byte verification. Record completed scan dates/counts separately from reanalysis attempts and in-progress results.
- For new reversible automation triggers that directly extend Companion Auto Summon's core behavior, default the option ON for fresh profiles and set it ON during upgrades only when that new preference is absent. Never overwrite an existing player choice. Keep the master automation switch and destination-location controls authoritative, provide a clear in-game OFF control, and explain the new behavior/default in release notes. This rule does not set defaults for gameplay-altering, resource-cost, or other features outside core automatic summoning; decide those separately.
- Treat death/respawn as its own automatic-summon trigger, separate from save-load and teleport arrival. Only a verified completed respawn for the local player may create an opportunity; never infer it from a shared movement/position helper or a generic warp. Preserve the master switch, destination controls and all native manual summon eligibility and placement checks.
- Keep native ownership, eligibility and placement rules intact. Do not generate or unlock pets, lower existing gameplay limits or write game save files. The approved earned exosuit-technology design may add its own recipes and energy cost; prototype it offline until native registration, transactions, persistence and removal are verified. Never grant prototype inventory to the player's normal save.
- Keep the exact executable guard and use verified native mappings. A new game build is not supported until its mapping and behavior have been checked. Unknown or unreadable versions must disable native integration before hooks or native calls. The final launcher must explain this outside the game, with maintained translations and no unsafe override; a disabled runtime alone does not establish safety for saved custom technologies.
- In every version report, keep four identities separate: the game release/store build/executable SHA-256, the Git source revision, the distributed mod package version, and the exact game identity that compatibility evidence covers. A newer package number does not imply support for a newer game build. When asked to update this GitHub mod for a game patch, inspect and port the source against that exact build; do not substitute installing the latest Nexus archive unless the user asked to update the locally installed package.
- Keep build-specific native function/global RVAs, return filters and load-state policies in `native_mappings.json`. Generate C++ constants and derive build/validation/package receipt expectations from that same exact release/build/hash entry. Never select mappings from a game or package label alone. Research entries retain `activation_approved=false`; a profile edit alone must not enable them. Inventory the selected table plus its source consumers and add new policy dependencies to the exact-build ledger instead of silently retaining an old denominator.
- Treat game-version mapping as an automatic, required project step whenever a new NMS executable/build is detected or native mappings change; do not wait for the owner to remind you. Update `docs/research/NATIVE-UPDATE-MAP.md` and the build-specific compatibility/research report in the same work period. Record the executable identity (game release, Steam build where available, file version, size and SHA-256), exact analysis tools/versions and reproducible search steps, candidate and verified function RVAs/signatures, function boundaries/callers/ABI and local-player versus network semantics, plus static/live test evidence. For x64 code references, decode within PE exception-function ranges (`.pdata`) and confirm instruction boundaries; whole-section linear sweeps are discovery only and cannot prove caller counts or that references are absent. Mark every lead as confirmed, rejected or still unverified, with the reason and any useful false lead, so the next update can reuse the map rather than restart discovery. Cross-link the map from affected compatibility notes and update behavior/changelog/known-issue records before packaging or claiming support. If semantic or live evidence is missing, say so explicitly and keep the integration disabled. Never commit game binaries, save data or raw copyrighted disassembly; preserve only concise, original analysis and reproducible metadata.
- Pattern discovery is a required gate on every new executable and whenever a native dependency changes. Follow `docs/research/NATIVE-PATTERN-PLAYBOOK.md` without waiting for a reminder. In the exact-build report, preserve a per-dependency ledger of successful matches, zero/multiple matches, false leads, corrected interpretations and `NOT CHECKED` work, with exact input hashes, pinned pattern-source revision, tool versions and commands. Reuse validated work only when its recorded cache inputs still match; always rescan the required source dependency inventory against a new executable hash. Summarize reusable successes and dead ends in `docs/research/NATIVE-UPDATE-MAP.md`, and append a dated handoff to both documents before ending a compatibility work period. A unique byte match is never by itself permission to change a profile or source mapping.
- Preserve a dated, actionable handoff in both the reusable map and the exact-build report after every compatibility work period, including when no source/profile change is safe. Carry forward what was already established; record useful new methods, observations, corrections to earlier interpretations, misleading approaches, checks deferred or omitted, and the next bounded action with the evidence it should produce. Mark work that was not checked as `NOT CHECKED` instead of leaving it implicit. Keep concise original findings and exact tool/command parameters; do not copy bulk disassembly or raw output into Git.
- Run each compatibility pass from a compact gate table derived from the source dependency inventory. Give each dependency a stable role, evidence-backed state (`MAPPED`, `PARTIAL`, `FALSE LEAD` or `NOT CHECKED`), its exact-build evidence link, the feature/release gate it blocks, and one bounded next action with expected evidence. Prioritize the shortest critical path to a complete requested behavior; do not mistake scan volume or documentation changes for port progress. After a bounded attempt that adds no evidence, record why and switch to a new evidence source or an independent unresolved gate instead of repeating the same search. Do not end a work period after documentation alone while an authorized, actionable analysis step remains.
- Plan runtime evidence during the first work period of every native game update. For each unresolved behavior/state/field question, state whether a bounded read-only game observation can distinguish the candidates. After one bounded static attempt adds no evidence to a runtime-observable question, prepare the smallest safe observation and request the specific player action before another broad scan. Do not postpone runtime work until all static roles are mapped. If launch/read-only inspection is already authorized, use that authorization and existing backup/identity rules; otherwise ask only for the missing consequential action. Continue independent work while awaiting the player.
- Every player-assisted observation needs a named question, exact executable identity, a baseline, one short plain-language action, the after-state, and an explicit interpretation limit. Ask for one short action at a time and confirm the capture before asking for the next. Prefer passive external reads before any hook or deployment; retain the exact-build/process guard and keep unsupported integration disabled. A read-only observation does not validate an uninstalled mod. Record all intervening actions, including ship entry or location changes, and do not attribute an ambiguous change to only one of them. If native UI control is unavailable, ask the player to operate it rather than claiming an action was automated.
- Verify new event-filter predicates at the actual callback boundary, including before/after native forwarding and the exact caller. Record the first refusal with bounded nonpersonal diagnostics during a controlled trial. An applied state seen later in a load does not establish that it is active at the earlier data-load callback. Keep explicit known death/foreign-caller refusal, native readiness and eligibility authoritative. Fix a demonstrated timing mismatch through the verified caller/owner contract; do not silently weaken an unrelated safety check.
- Record and reuse the minimal observation tool/command, its hash, observed menu/lifecycle state, sanitized result, unsuccessful attempts and the next discriminator in both native update handoffs. A successful Steam launch request is not proof the game started; verify the actual process. Resolve private save/backup locations in the real authorized desktop context: sandbox environment variables can point to different directories. Never claim a denied or incomplete backup was verified, weaken its ACL to make it pass, or print account/save identifiers while diagnosing it.
- Print a successfully read baseline in the capture's ready record before requesting a timed player action. Record duration, interval, sample/change counts, after-state and the player's confirmation separately. If a longer repeated poll still observes no transition, stop repeating the same action/method; change the evidence source or anchor. An after-state reason change is an association, not a captured callback or proof of completion.
- Before searching an unresolved relationship, search the exact-build ledger for both endpoint roles, helper RVAs and vector-header bases. Reconnect existing hash-matched producer/copy/consumer evidence before requiring pointer aliasing or starting another broad scan. When the relationship closes, update the stable role and link its evidence; mark earlier next actions and contradicted interpretations as superseded.
- For every data-field mapping, record the exact access width and read/write direction, the base object and how it is derived, and the def-use chain tying it to the owning consumer. An offset match alone is only a candidate; it does not identify a field or establish that the source and target layouts agree.
- Normalize field addresses to each proven enclosing owner before searching setters: if `owner=app+offset`, batch both `owner+field` and the composed `app+(offset+field)` displacement. Include enclosing wider stores when relevant. An owner-relative zero does not exclude application-relative writers.
- Simplify complete pointer arithmetic before comparing field offsets, including cancelling scaled terms and interior pointers. Kill register provenance on every redefinition. A context descriptor at `base+4` and a copied source row at `base+0x80` must keep distinct field names even when their instructions show familiar displacements.
- For constructor loops, derive the initialized element count from the counter and branch, and distinguish the last initialized element from the pointer after the final increment. A pointer advanced to the next element does not establish another constructed element or an overlapping subobject.
- For state and index fields, trace at least one exact setter and clearer/transition, record sentinel values, and follow one consumer to its indexed object or behavior. If producer and consumer use different fields, trace the exact copy/assignment between them and check whether an intervening callee can change the value. Confirm the base object independently; a familiar source name or matching displacement does not prove the target meaning. When the tool supports it, batch exact read and write filters in one full-image pass instead of decoding the same ranges separately.
- For serialized save fields, trace the exact-width initializer, save-side copy into the common state object, and load-side copy back into the runtime state through the same base object. This can map the static field contract, but a matching qword alone does not prove a unique save identity or local-versus-network behavior; keep those runtime semantics as separate gates.
- For virtual-call discovery, derive the receiver and each argument at the dispatch after the last intervening call, resolve chained `.pdata` ranges before scanning callers, and confirm the receiver's class through RTTI/constructor or another exact owner chain. ABI-shape tools and same-slot results are candidate filters only.
- When a nested receiver is assembled through register-held constants or arithmetic, propagate those values to the dispatch (for example `mov reg, immediate; lea owner+reg` or `imul` followed by `add`/`lea`). The function's incoming `RCX` and a direct caller's argument do not by themselves identify a later virtual-call receiver; record the wrapper receiver and nested receiver separately.
- In indirect-call scans, distinguish an embedded object built with `lea owner+offset` from a pointer loaded with `mov [owner+offset]`; track whether each register holds an object, vptr, or loaded method pointer, and apply the virtual-call slot displacement exactly once. A one-`.pdata`-range hit or zero remains bounded until the complete chained group and exact receiver/arguments are checked.
- For every native detour, reconcile the physical Win64 argument slots with the callee's full chained `.pdata` group. Derive home/stack offsets from the actual prologue; record each slot's first read, write or address escape and its access width. A narrow caller store, a saved volatile register, or later mixed-width access to a reused slot does not establish the argument's type or meaning. If a slot is overwritten before the input is read or escapes, record that the candidate does not consume that input; do not assign source parameter names without an independently verified caller/runtime contract.
